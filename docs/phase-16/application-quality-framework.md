# Phase 16 — Application Quality Framework

## Functional Quality

The application must:

- Load required analytical artifacts.
- Reject missing artifacts clearly.
- Display valid store selections.
- Display demand metrics.
- Display inventory scenarios.
- Display model evaluation results.
- Explain the evidence behind each store's selected model, including the weaker
  single-fold basis of Store 4's configuration.
- Explain scenario assumptions.

| Requirement | Status | Evidence |
|---|---|---|
| Load artifacts | Met | `load_application_data()` reads all seven |
| Reject missing artifacts clearly | Met | `test_missing_artifacts_names_every_gap` |
| Valid store selections | Met | `test_store_ids_are_sorted_integers` |
| Demand metrics | Met | Rendered from `inventory_demand_summary.csv` |
| Inventory scenarios | Met | `test_filter_scenarios_*` |
| Model evaluation results | Met | Phase 11 comparison section |
| Per-store model evidence | Met | `test_evidence_matches_every_store_row` |
| Scenario assumptions explained | Met | `SCENARIO_ASSUMPTION_NOTE` rendered in the UI |

## Data Quality

Application inputs must:

- Exist.
- Be readable as CSV.
- Contain rows.
- Contain required identifiers.
- Preserve the analytical results generated by previous phases.

| Check | Method |
|---|---|
| Existence | Every name in `ARTIFACT_FILES` must be a regular file |
| Readable, non-empty | `load_csv` raises on read failure and on a frame with no rows |
| Identifiers present | `find_column` reports a missing identifier instead of raising `KeyError` |
| Results preserved | `test_deployment_bundle_matches_the_pipeline_output` compares the bundle to `data/analysis/` by SHA-256 |

The last check is the important one: because the deployment bundle is a copy,
the test asserts that it has not drifted from the pipeline output it mirrors.

## Software Quality

The application should:

- Use project-relative paths.
- Separate responsibilities.
- Avoid unnecessary dependencies.
- Use explicit error handling.
- Avoid secrets.
- Provide maintainable code.

| Quality | Status | Evidence |
|---|---|---|
| Project-relative paths | Met | `test_application_uses_project_relative_paths` |
| Separated responsibilities | Met | Five modules, one concern each |
| No unnecessary dependencies | Met | streamlit, pandas, numpy only |
| Explicit error handling | Met | Loader names every missing file before raising |
| No secrets | Met | `test_application_source_contains_no_secrets` |
| Import safe | Met | `test_module_imports_without_a_streamlit_runtime`, `test_no_streamlit_calls_run_at_module_scope` |

## Testing

The support layer is covered by automated tests, and the workflow is executed
end to end by a headless startup test that serves the application and asserts
HTTP 200.

| Suite | Tests | Result |
|---|---|---|
| `tests/test_application.py` | 36 | Pass |
| Full project suite | 530 | Pass (1 warning, 248.36s) |

The previously documented position — that the interface "must be manually
smoke-tested" — is retained as a manual step, but automated startup is now
covered as well so a broken entry point fails the suite.

## Reproducibility

The application is runnable using the documented environment and commands:

```
python -m pip install -r requirements.txt
python -m streamlit run app/streamlit_app.py
```

`requirements.txt` pins every version and `.python-version` pins the
interpreter. The deployment bundle makes the run reproducible from a fresh
clone even though `data/analysis/` is excluded from Git.

## Known Limitations

1. Automated tests do not replace human usability review of the rendered
   interface.
2. The application presents model evidence; it does not validate it. If the
   Phase 11 or 12 artifacts were wrong, the application would faithfully
   display wrong values. Input integrity is therefore a pipeline concern.
3. The hosted public deployment is pending owner authorisation.
