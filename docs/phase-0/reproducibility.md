# Reproducibility

## Objective

Another developer can reproduce the project workflow from the repository
documentation. The command-by-command procedure is in
[`../reproducibility-runbook.md`](../reproducibility-runbook.md).

## What the project records

- Python version
- R version
- Package dependencies
- Dataset source and license
- Dataset version where available
- Preprocessing decisions
- Feature-engineering decisions
- Model configurations
- Hyperparameters
- Evaluation metrics
- Random seeds where relevant
- Training/validation/test methodology
- Application configuration
- Deployment configuration

## Randomness

Random processes use explicit seeds. The feature-based candidate is fully
deterministic.

## Time-series reproducibility

The project preserves temporal ordering. Random shuffling is never used when it
would create temporal leakage.

## Data leakage

Training, validation and test periods remain separate and are contiguous and
non-overlapping by date. Test data is never used for model selection or tuning;
the reserved test period is never read by any stage.

## Environment

The Python environment uses a local `.venv` with pinned dependencies in
`requirements.txt`. R dependencies are recorded separately in
`data/analysis/r/r_environment.csv`, which the R workflow writes itself.

## Dataset

Raw data is not modified: the pipeline re-runs without changing a raw byte.
Processing scripts produce the processed datasets deterministically; the
integrated dataset is byte-identical on re-execution.

## Model reproducibility

Important model parameters are recorded in the Phase 12 configuration tables.
Final model artifacts are not persisted: the selected configurations are refit
from validated artifacts with fixed seeds, and the application never retrains.

## Results

Evaluation results are saved as artifacts and documented in the phase results
documents. Every reported result is generated by the pipeline and appears in its
artifact.
